# Web editor UX instructions

Keep the browser editor understandable and reliable for creating, opening, editing, validating, and saving WF workflows.

## Scope

- Apply UX changes to `WorkflowEditor.Web` and its required Web projects only.
- Do not change or migrate `WorkflowEditor.Win` or `glassPeople`.
- Keep this file to current behavior, open UX work, acceptance checks, and known limitations. Do not add implementation diaries or closed-step logs.
- Activity coverage and code patterns belong in [WORK_PLAN.md](WORK_PLAN.md).
- The pointer drives the editing surface: a drop, a connection and the `START` badge of a `Flowchart` are made with it, and a keyboard-only path for them is out of scope. Controls keep the accessible names they have, and a command that has a key (`Ctrl+Z`, `Ctrl+D`, `Ctrl+C`, `Ctrl+V`, `Delete`) keeps it.

## Already implemented

- New workflow starts with an empty `ActivityBuilder`; its root accepts one Activity. Toolbox is grouped by control flow, primitives, collections, flowchart, and state machine.
- Resizable/collapsible toolbox, variables, and properties panels. The canvas carries one tools panel at its bottom right: the zoom commands — zoom out, the current zoom (which resets it to 100 %), zoom in and fit — with the checkbox that shows the minimap in the same row (it starts off), and the map above them once it is switched on.
- An activity from the toolbox that is an open generic (`ForEach<T>`, `Switch<T>`, `Assign<T>`, the collection activities) is completed before it is placed: the drop opens a dialog that asks for a type per parameter, one field per parameter, each named by the parameter it fills, because the chosen type can itself need parameters (`List<T>` then asks for its element type in place).
- Every dialog is as narrow as the content it holds — a message, or one field per line — instead of the empty half of Bootstrap's large size: the width is set once, and a word of a message or of a type name that does not fit is broken rather than pushed out of the box. The dialogs use it: the message of a failed action or of a validation run, the confirmation of a variable deletion, and the one form that asks for a type — it completes the generic parameters of an activity that is dropped before the activity is placed, and it chooses the type of a variable; a field is named where a name says something (the generic parameter `T`) and asks for the type alone otherwise.
- Nested stack regions, Flowchart and StateMachine editing, directional connections, validation feedback, notes, dirty-state confirmation, and XAML open/save.
- The card header carries the activity icon (or, on a card that holds an editor, the chevron that switches the body between the two blocks in the place of that icon), the display name (truncated, full name in the tooltip) and the card actions; the body holds the note preview and the block the card is in. The `Open` action of a container card sits on the left as a command of that leading place, after the chevron of a card that holds an editor and first on a container card that has none, such as a `Flowchart`, so the two commands read in the order they are used. A command on that line takes the metrics of the chevron and not the ones of a link, so the header keeps its height when the selection brings out the remove command: neither the name nor the commands that stay there move. The remove command is shown on the selected card only, so a surface of many cards does not carry a red circle per card; the `Delete` key removes the selection as well. A connection does the same on its own scale: it offers its one command — removing it — once it is picked, drawn on the line at the middle of its route (a command that floated beside the line would be gone by the time the pointer reached it, because it does not belong to the link), they are small enough to sit on the line, the name of the branch the line carries is lifted above it so the two do not cover each other, and a picked or hovered connection says with a thicker line that it is a control of its own.
- Every activity edits its own fields on its card, and the body of a card carries one of two blocks: closed shows the compact fields a control passes as `Preview` (they are editable, so a closed card is still edited in place), open shows the editor it passes as `Edit` — for an ordered container that editor is the list of its children. The chevron switches between the two blocks, so it appears on a card whose control passes an editor and on no other: a card that only carries compact fields shows its activity icon instead of the chevron and has no closed state of its own.
- Designer notes are edited in the properties panel in a multi-line field that keeps the line breaks the user typed; the card previews the note, clamped to three lines, and the note is saved in XAML next to its activity.
- Validation has no panel of its own. A card whose activity reports errors, or that holds an activity reporting errors anywhere below it, is outlined in red, and the messages of the selected activity are listed in the properties panel. Every other card draws the same outline in a neutral color, so each box reads on the canvas; a picked card is outlined by its selection border instead, and a `Flowchart` start element keeps its own cue.
- Every card shares one width while it is collapsed, whatever activity family it belongs to, and a card drawn inside a branch region keeps that same width. The chevron opens a card without changing that width: an open card keeps it while its editor holds no nested card and grows past it only as far as the cards the editor draws need, so an activity with nothing inside it does not widen when it is opened and an owner card widens only as much as the branch cards it shows require.
- The place of a card is the center of its box. The browser measures the card after a render, and the library keeps the top-left corner of the box where it is, so the measure moves the center; a card therefore grows and shrinks around its center instead, which keeps the place the user put it and keeps it while its container is opened and left.
- Containers (`Sequence`, `Parallel`) are plain cards that keep a short body below the header, so an empty card still reads as a surface that holds the schema, because everything they hold is visible after opening them.
- A `Sequence` is edited in two ways, and both show the same children. Its card starts collapsed and draws the children inside itself, one under another in model order (a nested container draws its own children the same way, so the whole tree is cascaded), and the `Open` action shows them on a surface of their own as a column. A drop lands at the index of the drop point (a caret shows the place), a card dragged to another place takes it — including out of the list or branch that drew it and into any other target of the schema — `Alt+↑/↓` moves the selected card in the order (the properties panel says so), and the header keeps no move commands. A card of an ordered container has no ports or connections and keeps no position of its own (a `bwas:Designer.CenterX` left in an older file is ignored). Opening a card that is drawn inside another card puts the containers between them on the breadcrumb. `Parallel` stays a row of branches: its members are unordered, so it accepts drops and deletes only.
- An opened container that holds nothing yet asks for its first element in the middle of its surface, exactly like the empty root: the request is a plain line of text with no frame, because the surface draws nothing to point at. A branch that holds nothing keeps its dashed placeholder instead, because it sits inside the card that frames it.
- A card is dragged with the mouse, wherever it is drawn: out of the list of a `Sequence`, out of a branch region of an activity that holds one Activity per branch (`If`, `While`, `DoWhile`, `ForEach<T>`, `TryCatch`, `Switch<T>` — shown while that card is open), and out of the column of an opened container. The drop does not care what the source was: a list of another `Sequence` card, a branch region, a region of a container card and the column of the opened container all take it exactly as they take an activity from the toolbox, because the card carries the activity it shows and the drop moves it instead of creating a new one. The activity a branch already held is replaced and removed with its node, a card that leaves the column leaves the canvas with it, and a card is never dropped on a container it carries itself.
- Connection points are offered only by the elements a graph container lays out: inside an opened `Flowchart` or `StateMachine` a card shows its connection points when it is hovered, selected or expanded, and a link drawn between two of them becomes a model connection. A card of any other surface — the root, a `Sequence` (on its own surface and in the list its card draws) and a branch region — is placed by its container, so it shows no ports at all and cannot start a link. Every edge of a card offers three connection points — the middle one and one beside it on each side — and each of them joins a link in both directions: a connection is started at the point the drag begins and ends at the point it is dropped on, so the user picks the edge that gives the neatest route instead of remembering which edge means what, and the card the drag started from is the source of the connection. An edge that sets a named branch keeps a single point at its middle instead, because the name of the branch is drawn beside it. A card is still never connected to itself. A connection the model of the activity draws (a step that runs after another one, a branch of a decision, a case, a transition) takes the edges of the two cards that face each other, and the connections of a surface are drawn again when a card of it is dropped, so an arranged graph keeps short lines without the user drawing them over. The editor also has a mode (`Service.DynamicLinks`, switched in code while how to switch it is still open) in which a connection is bound to no point at all: the two ends are picked as a pair, by the cheapest route the two cards allow — measured with the router of the editor, corners weighed first — and taken again while a card is being moved, so the lines follow the cards and a connection that can leave a card downwards and arrive on the side of the other one is not wrapped around both cards because the two cards happen to lie in a row. Nothing is written to the schema in that mode, so the points a connection was given are still there when the mode is switched off; how the mode is switched is still open, so it is a property of the editor (a session setting) for now. A connection whose end the user dragged onto another connection point keeps that point — the edge of the card and the place on that edge — with the element the connection leaves from, so a schema that is saved and opened again draws the line on the very point it was left on instead of where the model alone would put it. The edge a connection is drawn from names the branch it sets: a card that keeps one outgoing branch (`FlowStep`, `State`) is re-pointed by drawing the connection again, the edges of a `FlowDecision` are pinned, because the names of its branches belong to them: it carries its entry on its top edge alone and its branches on its sides — `True` on the left edge and `False` on the right one, with nothing on the bottom edge (each edge carries the name of the branch it sets), and a `FlowSwitch<T>` adds a case from an edge of its own and sets or moves its default branch from the bottom one — so a connection is changed by drawing it over, not by deleting it first. A connection that is already on the canvas is changed in place as well: a press on the line near one of its ends takes that end, and a press on a connection point takes the connection that belongs to it — the one that arrives there, or, on a point nothing arrives at, the one that leaves from it, because the beginning of a line sits on the point of the card it leaves from and the line itself cannot be reached there; a point that adds connections next to the ones it carries (a case of a `FlowSwitch<T>`, a transition of a `State`) is never full and keeps drawing a new connection when it is pressed. Only that end follows the pointer — the end is taken when the pointer is pressed within a short reach of it and starts to follow once the pointer has moved, so a press on the line that does not move (or a press on the middle of a long line) picks the link instead of taking an end away —, so the connection is moved by its beginning or by its end and the end that did not move stays where it was, keeping the branch the connection leaves from. Dropping that end on another connection point moves the connection there, and a point the container refuses (a card into itself), a drop away from every connection point or a release the canvas never sees (the pointer left it while the end was moving) leaves the connection as it was — a connection is removed by its own command, not by dragging it away.
- Branches that hold a single activity (`If`, `While`, `DoWhile`, `ForEach<T>`, `TryCatch`, `Switch<T>`) are edited on the node card: they are the editor block of the card, so they are shown once the chevron opens it, and the branch renders the control of the activity it holds through a dynamic component, which can be selected to edit its properties. A container child keeps its `Open` action and is then edited through the path. These activities hold one activity per branch, so unlike `Sequence` and `Parallel` they are not containers and are never opened.
- A branch is a caption plus the control of the activity it holds, with no frame of its own, so the inner card stays the only border. An empty branch shows the same dashed drop placeholder as the start of a new schema. A branch takes a drop while the card that holds it is open: a card of a closed card shows its fields instead, so the chevron is the way to reach the branches.
- The card of an activity carries its properties as compact fields, and a card that holds branches keeps them above them: `If`, `While`, `DoWhile` their condition, `ForEach<T>` its values and item name, `Switch<T>` its expression and cases, `TryCatch` its catch type, `WriteLine` its text, `Delay` its duration, `Assign` its destination and source, and the collection activities their variables. `If` places Then and Else next to each other, and a card with branches shows the fields while it is closed and the fields with its branches while it is open.
- A graph container keeps the one choice that is not made inside it: `Flowchart` its start node and `StateMachine` its initial state. Both are the user's choice and neither is made by a drop: an element dropped into a graph container becomes a node of it and is connected to nothing, and while no start is chosen the surface of the `Flowchart` asks for that choice alone. The card of a `Flowchart` carries its name and its `Open` action alone — it is the size of any other collapsed container card, such as the card of a `Sequence` — because the start node is chosen on the surface it opens. A `FlowDecision` and a `FlowSwitch<T>` carry their condition, expression and targets, and a state carries its entry, exit, transitions, and its initial/final flags. The `START` badge of the opened `Flowchart` is the handle that makes that one choice without leaving the canvas: it is dragged onto the card that should run first, which is outlined in the color of the badge while the drag points at it, and the surface draws no cue of its own while a start node is chosen.
- Editing a property on a card or in the properties panel marks the schema as changed and refreshes the diagram and the panel, because the model setters notify the service.
- The variables of a scope are edited in place in the panel: a row carries the fields of the variable it shows — the name and the default value are text fields, and the type is a link that opens the same dialog that asks for the type of a dropped activity, because a type can need parameters of its own (`List<Int32>`). The table keeps no header row and no edit command per row, so a row reads as the variable it is; every field names itself for the screen reader. An edit is committed when the field is left or entered, a name that is empty or unchanged is refused and the field shows the name the variable has, and an edited variable keeps its place in the list. The rows of a scope form one grid, which flows into as many columns as the width of the panel allows and falls back to a single column when the panel is narrow: the panel is wide and short, so a scope of many variables is read and scrolled in the place the panel has instead of in one long list. The header of each scope says how many variables it holds, also while it is collapsed, and stays in view while the rows of that scope scroll under it. The add command adds a row with a free name for the user to rename, and the delete command asks for a confirmation.
- The page commands live in one toolbar row of icons — new, open, save, validate and the theme — with the tooltip and the accessible name carrying what each one does, and no hidden submenu: the theme button switches to the other theme and shows the one it switches to. The row keeps the unsaved-change pill, which states the state in words because it reports it rather than acting on it.
- Light/dark theme toggle persisted in `localStorage`.
- Properties panel supports display name plus focused editors for Assign, WriteLine, Delay, If, While, and AddToCollection. Dedicated node editors cover additional activities; an activity without an editor of its own keeps an explicit fallback that names the two fields the panel always edits, so nothing reads as an activity with no place to be edited.
- The panel states the context of the activity it shows, so where that activity is edited is never a guess: the kind of the activity comes first, then one line that says the panel edits its fields while the card keeps its own, that a container edits its children on the surface its card opens (`Open`, or a double click), or that an activity holding one Activity per branch edits each branch in the region the chevron of its card opens.
- A variable belongs to a scope, so the panel says which one owns every group and where a new one lands. The header of a group carries the display name of the scope and the kind of activity that holds it (`Sequence`, `While`, `ActivityBuilder` for the workflow root), which tells two scopes of the same kind apart, and the group a new variable lands in is marked. The add command names that scope in its tooltip and its accessible name, and while no activity of the opened path holds variables the command is unavailable and the panel says why instead of changing nothing. The state of a collapsed group belongs to the scope and not to its name, and the variables of a scope are listed for the surface that was just settled, without the next navigation.
- A variable is part of the schema: adding, renaming or retyping one marks the workflow as changed, so the editor records the step of the history, offers to save it and keeps it in the draft, exactly like an edit of a card.

## Active UX priorities

1. **Root, Sequence and branch semantics:** keep a new workflow empty until the user adds its single root Activity; reject a second drop at the `ActivityBuilder` root. Show a presentation-only `START` cue only on a `Flowchart`, where the start node is a choice of the user (it marks the chosen node on its card, and asks for a node or for the choice itself while there is none); every other surface — the root, `Sequence`, `Parallel`, `StateMachine` — only draws a drop hint while it holds no element yet, with no `START` badge. Add or arrange Sequence children only after opening the Sequence. An activity that holds one Activity per branch (`If`, `While`, `DoWhile`, `ForEach<T>`, `TryCatch`, `Switch<T>`) fills only the branch the drop landed on and renders it inside its own card, so it is never opened.
2. **Workflow Foundation visual comparison:** use the legacy desktop editor as a read-only reference, not as a migration target. Compare its activity toolbox, property inspector, commands, toolbar views, and design surface with the Web editor, then resolve the remaining Web UX gaps. Reference composition: [MainWindow.xaml](../WorkflowEditor.Win/MainWindow.xaml), [MainWindow.xaml.cs](../WorkflowEditor.Win/MainWindow.xaml.cs), and [DesignerService.cs](../WorkflowEditor.Win/DesignerService.cs).
3. **Sequence editing:** the children of an opened `Sequence` form a column (the "ordered container"): the model order decides the place of every card, a drop lands at the index of the drop point, and a card the user drags — or moves with `Alt+↑/↓` — takes a new index. A card of the column is dragged as a card, so it can also leave the column for another target; moving a node can never silently change the execution order in another way.
4. **Variables panel rework:** the owner wants this panel rethought instead of patched again, so the row of fields per variable, the grouping by the scope that holds it, the grid and the single place this panel has at the bottom of the page are all open to replacement. Settle the direction with the owner first: what the panel has to answer at a glance (which variable, of which type, whose scope it belongs to, where it can be used), how a scope of many variables is browsed and searched instead of scrolled, whether the arguments of the workflow are listed beside the variables, and where the panel belongs in the layout — beside the diagram, in a dialog, or beside the properties of the selected activity. Until that direction is chosen the behavior recorded below stays as it is, and another change of the rows alone is not the rework that was asked for.
5. **Responsive layout (lower priority):** keep the editor usable at narrow sizes, but prioritize the large-screen workflow canvas used for diagram editing.

## Acceptance checks

- A new workflow has no implicit Sequence; adding one root Activity succeeds, a second root drop is rejected, and deleting the root allows a new one.
- Only the `Flowchart` draws a `START` cue: the badge and the arrow sit above the card of the chosen start node, and while no start node is chosen the canvas draws the badge, the arrow and a drop box at the top. Every other surface — the root, `Sequence`, `Parallel`, `StateMachine` — draws no `START` badge at all and, while it holds nothing, only the drop box asking for its first element. The cue is never serialized or editable as an Activity. The badge is the handle of that choice: dragging it onto a card of the open `Flowchart` makes that card the start node — the card under the drag is outlined while it is the target, the badge and the arrow move to the card that was dropped on, and the container card shows the same choice by carrying the marker. Dropping the badge on the card that already starts the flowchart, or outside every card, leaves the model as it was.
- An empty root asks for the first activity with that drop hint alone; an unset Flowchart start is clearly indicated — the canvas asks for the node that runs first and carries the badge the choice is made with. The initial root activity is centered in the visible editor area, including when the editor is first rendered before its canvas dimensions are known.
- A Sequence card starts collapsed — a newly added Sequence is never opened in edit mode by itself — and the collapsed card does not accept drops and shows no children: the chevron of the card opens and closes the list it draws, and `Open` shows the same children on a surface of their own. The state of the chevron is kept with the activity (`bwas:Designer.IsExpanded`, written only while the card is open), so opening a container and coming back, or saving and reopening the schema, shows the card as the user left it.
- Inside a Sequence, both on the card and on its own surface: a dropped activity lands at the index of the drop point, a dragged card and `Alt+↑/↓` move an element to another index, the first and last card of a column cannot move out of it, deleting a card closes the gap, and selecting a card drawn inside a card fills the properties panel. The order survives save and reopen. A card is taken by any target that takes an activity from the toolbox — the list of another card of the same surface, the branch region of another activity, the region of a container card, the column of the opened container — whether it comes from a list, a branch or that column, so what draws it changes with it and the children it carries move along, while a card dropped on a target it carries itself, or on a target that refuses it, stays where it is. The caret a drag showed is gone once the drag is over.
- A drop into an opened `Flowchart` or `StateMachine` adds the element as a node of that container and connects nothing: no step runs after another one, and no start node is chosen, until the user draws the connection and drags the `START` badge.
- Selecting a card outside a graph container shows no connection points; inside an opened `Flowchart` or `StateMachine`, a selected element still offers its connection points and a link drawn between two elements becomes a model connection. Any point of a card starts a link and any point of another card receives it, whatever edge each of them is, while a card still cannot be connected to itself. A connection drawn from a card that keeps one outgoing branch takes the place of the one it had, and a `FlowDecision` or `FlowSwitch<T>` states on its edges which branch each of them sets, so the second connection drawn from the same edge replaces that branch and leaves the others where they are. A picked connection draws its one command on the line at the middle of its route, and that command removes the connection; the connection itself is moved by taking one of its ends — on the line, where the press takes the end of the route it is nearest to, or on a connection point, where the press takes the connection that belongs to it — the one that ends there, or, on a point nothing arrives at, the one that leaves from it, so a connection is grabbed by its beginning as well as its end; a point that adds connections (a case of a `FlowSwitch<T>`, a transition of a `State`) holds no connection of its own and keeps drawing a new one — and dropping it on another connection point, which keeps the branch the connection leaves and leaves the connection as it was when the drop is refused or lands away from every point. Deleting a node that was the start of `Flowchart` hands the start to the node that ran after it (the first branch of a decision or a switch), so the flowchart keeps a start node; a node that nothing points at any more stays on the canvas as the node it is.
- A branch is filled only when the drop lands on it of a card whose chevron is open, and the branch renders the control of the activity it holds; that control can be selected to edit its properties, and a container child keeps its `Open` action, which opens it through the path. An activity that holds one activity per branch is not a container and is never opened itself. Deleting or replacing a branch child releases the model reference, and a card that grew is laid out again so it does not overlap the next card.
- On the primary large-screen layout, the design surface, toolbox, properties, variables, commands, and navigation have clear roles and do not hide essential actions.
- A variable is added, renamed, retyped and given a default value in its own row, without opening a form and without an edit command per row: leaving a field or pressing Enter commits the change, a name left empty is refused rather than producing a nameless variable, the type is chosen in the dialog the type link opens, and the row keeps its place in the list.
- A scope of many variables is read and scrolled in the space the panel has: the rows of a scope form a grid of as many columns as its width allows (one when the panel is narrow), a row keeps the four controls of its variable in the order they are read and tabbed through, the header of the scope says how many variables it holds — also while it is collapsed — and the header stays in view while its rows scroll under it.
- The variables panel says which scope owns every group of rows and where a new variable lands: the header of a group names the scope and the kind of activity that holds it, the group the add command fills is marked and named by that command, and the state of a collapsed group follows the scope rather than its name. The command is unavailable, with the reason on the panel, while no activity of the opened path holds variables — a workflow whose root keeps none, a branch that keeps none of its own — and it fills the nearest scope that does wherever it is available. Adding, renaming or retyping a variable marks the workflow as unsaved, and the variable is in the draft and in the step the undo takes back.
- The properties panel states where the selected activity is edited: a container says its children are edited on the surface the card opens, an activity that holds one Activity per branch says they are edited in the region the chevron opens, any other activity says its fields are edited on its card while the panel shows the ones it supports, and an activity without an editor of its own keeps a fallback naming the display name and the note it always edits.
- A workflow that was just opened, restored from a draft, or put back by an undo lists the variables of its scopes at once, under the scope that owns them, without waiting for the next navigation.
- Every command of the toolbar is an icon that names itself in its tooltip and its accessible name, and each one is reachable with `Tab` and shows a focus ring; the theme button switches the theme in one click, without a menu, and its icon and tooltip state the theme the click switches to.
- A user can search for and add an Activity with keyboard and pointer; empty search results are explained.
- Selection, nested navigation, and loading a workflow keep the properties panel in sync.
- A note typed in the properties panel appears on the card immediately, keeps its line breaks through save and reopen, and the card preview never exceeds three lines.
- Invalid field values produce visible feedback and can be corrected.
- An activity with a missing required argument, or holding one, is outlined in red on the diagram; selecting it lists its messages in the properties panel, and no card carries an error badge.
- The example library of activities plugs in without a change to the editor: `TestBranch<T>` is dropped from the toolbox group of its own project, the dialog asks for the type of its single input (`TestInput` among the types offered), the card shows that field and one region per branch, a drop fills the branch it landed on, the validation of the schema lists the branches that are still empty with the message of the activity itself, and saving and reopening keeps the type parameter, the three branches and the expression of the input.
- The toolbar validation command reports the run in one dialog: it lists every message with the errors before the warnings and names the argument each one belongs to, a run without a message says the workflow is valid, a run with warnings alone lists them without marking a card, and a long list scrolls instead of pushing the button of the dialog out of the window.
- A schema with unsaved changes survives a reload of the page: the browser asks before the unload, the draft is offered back when the editor starts, restoring it shows the schema as unsaved, and the draft is gone once the workflow is saved, another one is opened, or the user discards it.
- Undo takes a burst of edits back and redo applies it again, with `Ctrl+Z` and `Ctrl+Y` (also `Ctrl+Shift+Z`) on the canvas and with the two toolbar commands: either command is shown as unavailable while it has nothing to offer, one step covers a burst of edits rather than one keystroke, and undoing back to the state the workflow was opened or saved in shows the workflow as saved again. Undo and redo return to the root surface.
- A copy of a card is added by `Ctrl+D` or by the command of the selected card: it takes the place right behind the original in the same list, appears where the original does (on the surface of the opened container, or inside the card that draws it), carries the arguments, the variables and the view state of the original while sharing nothing with it, becomes the selected card, and joins nothing on a graph surface. The root activity and a branch hold a single element, so they are refused, as is an element that is not the activity of its card (a `FlowDecision`, a `FlowSwitch<T>`, a `State`).
- `Ctrl+C` copies the card selected last and `Ctrl+V` adds a copy of it to the end of the opened container: the copy arrives selected, it carries the arguments and the view state of what was copied while sharing nothing with it, the same element can be pasted more than once, and pasting into a container that does not take the element changes nothing.
- Sequence and graph edits preserve their model semantics through save and reopen.
- Narrow viewport layouts remain usable without making essential navigation or actions unreachable.
- Light and dark themes retain readable text, links, ports, validation messages, and focus indicators.

## Verification and known limits

- Run the unit tests and Release Web build from the repository root; manually check the browser after restarting the host following a rebuild.
- Exercise empty, nested, graph, invalid, and large workflows on the primary large-screen layout; reload the page with unsaved changes and with a stored draft; check narrow sizes as secondary coverage.
- The toolbox panel, the dialogs, the search of the properties panel and the editor component are covered by bUnit tests (`Blazor.WorkflowEditor.Tests`), which run in CI; what a test cannot see — dragging, dropping, connections, the geometry of the cards and what the browser paints — is checked by hand in the browser.
- The undo history keeps 20 steps or 2 M characters of XAML, whichever comes first, and a step is a burst of edits: the editor records one 250 ms after the last edit of a burst, so an undo takes back a group of edits rather than one character. `Ctrl+Z` belongs to the canvas and needs its focus; inside a field of the properties panel or the variables panel the browser keeps its own undo for the text being typed.
- The cards drawn inside another card keep their selection when a second one is picked, so the commands that act on one card — `Ctrl+D` and the properties panel — work on the card picked last. A copy is made from the element of a card, so a `FlowDecision`, a `FlowSwitch<T>` or a `State` is not copied: a copy of one would join nothing and would have nothing to run.
- Publish with trimming and Windows view-state interoperability have not been verified.
- A designer that lives in a library of its own needs `Microsoft.AspNetCore.Components.Web` in its `_Imports.razor`, and the type list of the drop dialog is not filtered by the generic constraints of the activity being dropped.
- The ends of a connection are picked again while a card that can meet the band of that connection moves, and only then: a card dragged far from a connection leaves its ends where they are, even if the router would have moved them (a connection the user pointed somewhere keeps that choice until a card near it moves, or until the container draws its connections again).
- Graph layout is basic and does not minimize link crossings by itself: the cards are arranged by the user, while a route keeps its own distance from every card of the surface (a connection of a crowded schema falls back to the reach of the connection points, which is the narrowest a right-angled route can be), prefers the shortest run with the fewest bends, and a connection takes the edges that face the two cards it joins — an edge that stands for a named branch never moves on its own (in the mode above the two ends are picked together instead, by the cheapest route of the two cards); the connection point a hand-picked end of a connection was dropped on — its edge and the place on that edge — is kept with the element the connection leaves from, so it outlives a save and a reload; link bends are not draggable, and a connection is moved by taking either of its ends — on the line, or on the connection point the end arrives at.
- The variables panel is the one part of the editor the owner wants reworked (see the priority above): what the section on implemented behavior records about it describes the panel as it is now, and not the shape it is meant to take.
- The `START` badge is a pointer handle: the start node is chosen by dragging the badge onto the card that runs first, and the card of a `Flowchart` carries no list of nodes to choose it from (it is the size of any other container card), so that one choice is made with the pointer only — no keyboard path is planned for it.
- The children of a `Sequence` have no scrolling or fit action of their own: a long sequence keeps growing downwards, on its card and on its own surface, so a deep tree is reached by panning (and a deeply nested tree makes tall cards). A `bwas:Designer.CenterX`/`CenterY` left on a Sequence child by an older build stays in the file (it is ignored, not rewritten).
