# Web editor implementation guide

Use this file for current implementation state and engineering rules. The visual UX backlog is in [VISUAL_EDITOR_PLAN.md](VISUAL_EDITOR_PLAN.md).

## Boundaries

- Change `WorkflowEditor.Web` and projects required by its build only.
- Do not change or migrate `WorkflowEditor.Win` or `glassPeople`.
- Preserve WF XAML load/save behavior. Keep user Activity separate from the legacy Windows library.
- Web projects target .NET 10; do not upgrade unrelated solution projects.
- `Service` is one class in several files, by topic: the state, the lifecycle and the path the editor is on stay in `Service.cs`, the connections in `Service.Links.cs`, the cards and their commands in `Service.Cards.cs`, the graph surfaces in `Service.Graph.cs`, the validation in `Service.Validation.cs`, the undo history in `Service.History.cs` and the variables in `Service.Variables.cs`. A new member goes into the file of its topic; a member that another topic needs is `internal` or public rather than copied.

## Current state

- Dependency graph: `WorkflowEditor.Web` → `Blazor.WorkflowEditor` and `WorkflowEditor.TestActivities`; tests reference both libraries. The Web graph has no `glassPeople` reference or toolbox scan.
- `WorkflowEditor.Web`, `Blazor.WorkflowEditor`, and `Blazor.WorkflowEditor.Tests` target `net10.0`. Package versions are pinned in their project files, and the review of newer ones is done: `Microsoft.AspNetCore.Components.*` follow the latest patch of .NET 10, `Z.Blazor.Diagrams` is current, and `UiPath.Workflow` / `UiPath.Workflow.Runtime` stay at 6.0.3, the version the projects restore from their sources. The library describes itself to the package manager (`Authors`, `Description`, `PackageTags`, the MIT license expression, the repository URL, and `PACKAGE.md` as the readme of the package).
- XAML open/save, workflow validation, unsaved-change confirmation, and browser file download are implemented; a failed open/save/validate and an operation the editor refuses are reported in a dialog (`MessageModal`), so the page keeps no status line of its own. A variable is edited in its row, so neither adding nor editing one uses a form: the panel opens two dialogs, the confirmation of a deletion (`ConfirmationModal`) and the choice of a type (`TypeSelectModal`, the same form that completes the generic parameters of an activity that is dropped). That form offers the types that meet the constraints of the generic parameter each of its fields fills (`GenericTypeConstraints`: a reference type or a value type, a type that can be constructed, a type assignable to a constraint — and no nullable type where a value type is asked for), so an activity that constrains its parameter never receives a type it cannot take, and a type that only the completed choice can be judged by (`List<int>` for a parameter that asks for a list of text) is refused when the form is applied, with the parameter it does not fill, instead of failing the drop. A field shows the parameter it fills and what that parameter requires, a type reads as its own name with the types that complete it (`List<Int32>`, and `List<T>` while it is not complete — `Extensions.DisplayName`), the CLR name of a type stays in the tooltip of its row and matches the search of a picker as well, and the message of a refusal uses the short name too. A variable whose type is a nullable one keeps the default value typed in its row, which is converted from the type the nullable type holds. The rows of a scope form one grid, which flows into as many columns as the width of the panel allows — the panel is wide and short, so a scope of many variables is read in that space instead of in one long list — and the header of the scope carries the number of variables it holds and stays in view while they scroll under it. Every scope whose variables a card lists is a scope the panel can change as well (`Service.CanHoldVariables` answers from the collection the commands work on), because a scope that is missing there would list its variables and refuse to change them without a word. A variable belongs to the innermost activity of the opened path that holds variables (`Service.VariableScope`): a surface without variables of its own resolves outwards to the nearest scope that has them, the panel names that scope in its add command and marks its group, and a workflow whose path holds none disables the command and says why. A variable command is an edit of the schema like any other — it marks the workflow as changed, so the editor records the step, offers to save and keeps the draft — and the panel is filled once the surface has settled, so a workflow that was just opened, restored from a draft, or put back by an undo lists the variables of its root at once. The properties panel states the context of the selected activity: the kind of activity, where its fields are edited (here or on its card), and how its child region is reached — the surface a container card opens, or the branch regions a card that holds one Activity per branch shows when its chevron is open. An activity without an editor of its own keeps an explicit fallback naming the two fields the panel always edits. A new `ActivityBuilder` starts empty and holds one root implementation Activity; only a `Flowchart` draws a `START` cue (the root and every other surface just ask for their first element), and the cue is never part of the schema: it marks the node that starts the flowchart and it is the handle that re-binds that choice. Web view state and notes use `bwas:Designer` attached properties. A control the editor draws marks the keyboard focus: a `.btn` of the library draws an outline when the keyboard reached it (`:focus-visible`) and none when it was clicked, while the glow Bootstrap gives a focused button is left out, and the toolbar commands of the page, the panel headers, the chevron of a card and the splitter draw their own indicator. Validation returns a `ValidationReport` with the errors and the warnings of the run: the errors still mark the cards and are listed in the properties panel, while the dialog of the toolbar command lists every message of the run, the errors before the warnings, each one with the name of the argument it belongs to. A schema with unsaved changes is also kept as a draft in the browser (`localStorage`, never on a server): the page writes it shortly after the last edit, the browser asks before a reload or a close (`beforeunload`), and the draft is offered back when the editor starts — restoring it loads the schema as changed, and the draft is dropped once the workflow is saved, another one is opened, or the user discards it.
- Specialized designers cover `Sequence`, `If`, `While`, `DoWhile`, `ForEach<T>`, `Parallel`, `TryCatch`, `Switch<T>`, `Assign`/`Assign<T>`, `WriteLine`, `Delay`, `Throw`, `TerminateWorkflow`, collection activities, `Flowchart`/`FlowDecision`/`FlowSwitch<T>`, and `StateMachine`/`State`.
- `WorkflowEditor.TestActivities` is the worked example of an activity a user of the editor wrote, outside the editor library: `TestBranch<T>` takes one input and holds three branches, of which it draws one at random when it runs. Nothing in the editor names that project — the card is found by scanning the loaded assemblies for `[Pair]`, the card is a generic component built with the type the user picked in the drop dialog, and its three branches are `IActivityHolder` slots rendered with `EmbeddedActivity` — and the schema it writes is read back as it was saved, `x:TypeArguments`, branches and the expression of the input included. The activity closes over whatever type the dialog offers (it is not constrained, and every type the dialog offers meets the constraints of the parameter it fills), its branches read the value that came in through their own argument (`inputValue`), and the activity reports a validation error for each branch the user has not filled yet, so the editor lists them.
- The undo and redo commands (`Ctrl+Z`, `Ctrl+Y`, `Ctrl+Shift+Z`, or the two toolbar commands, which are shown unavailable while they have nothing to offer) walk a history of the schema: a step is the schema as XAML — so it carries the view properties of the cards, their position and note and expanded state — recorded by `Editor` once a burst of edits has settled, and the history is bounded to 20 steps or 2 M characters of XAML. `New`, `Open` and `Edit` start a new history, and a draft restored from the browser is not a saved state, so undoing back to it still asks for a save. The current step is compared with the one the schema was saved in: undoing back to that step clears the unsaved-changes flag. Every step is restored as a schema of its own, so undo and redo put the root surface back and clear the selection.
- A card that moves takes the ends of the connections it can meet with it, and only those: `Service.FollowCards` asks `WorkflowRouter.MeetsCorridor` for each connection, which answers whether the moved card stands in the band a route between the two cards of that connection is searched in at all. A card outside every such band leaves each cost of the connection as it was, so the pair of points that was picked is still the cheapest one and the connection is left alone instead of being measured again: measuring every connection of a 40-card flowchart cost about 7 ms per frame of a drag on a development machine, and only 4 of its 39 connections are measured now (a probe over that surface reports every cost of the rest as unchanged).
- `Ctrl+D`, or the command a selected card carries (`Duplicate this activity`), copies the activity that card shows and places the copy right behind it, inside the same container or the same list, and the copy takes the selection over. `Ctrl+C` copies the same card into a clipboard the editor keeps in memory, and `Ctrl+V` adds a copy of it to the end of the opened container, selecting it; the element stays on the clipboard, so it can be pasted again. A copy is written as a schema of its own and read back, so it carries the arguments, the variables and the view properties of the original without sharing anything with it, and it joins nothing on a graph surface: an element is copied, not its connections. Nothing is copied by a place that holds one element already — the root of the workflow, the branch of a card — nor by an element that is not the activity of its card (`FlowDecision`, `FlowSwitch<T>`, `State`): the step of a `Flowchart` holds the activity it runs, and that activity is what is copied. A paste into a container that does not take the element is refused in silence, like a drop the container refuses.
- Activities that hold one Activity per branch expose those branches as `IActivityHolder` slots (`DefaultNode.Slots`) and are not containers, so they never place their children on the parent surface and are never opened. Each branch renders the control of the activity it holds as an embedded node (`EmbeddedActivity` + `DynamicComponent`), created by `Service` in `updatePath`; the child can be selected to edit its properties, and a container child keeps its `Open` action and is then edited through the path. Such a card passes its fields as `Preview` and its regions, with those same fields above them, as `Edit`, so its branches appear once the chevron opens the card. `Sequence` and `Parallel` stay containers that list several children on their own surface. `Sequence` is an ordered container (`IStackContainer`): it lays its children out in model order, both as a column on its own surface and as a list drawn inside its card (`DefaultNode.InlineChildren` rendered through `SequenceControl`), a drop lands at the index of the drop point, and a dragged card or `Alt+↑/↓` moves an element to another index. Any card that another card draws is dragged as a card of its own (`Service.CanDragCard`): a branch child (`EmbeddedActivity`), a card of an inline list, and a card of the column of the opened container (`ActivityControl`), which takes its own pointer events so the diagram never moves the node under it. The drop of a dragged card is placed by the same code as a toolbox item (`Service.placeActivity`, which `AddActivity`, `Service.MoveDraggedActivity` and `Service.MoveInlineChild` share): the card keeps the activity it shows and only what draws it changes, so a branch region of another activity, a region of a container card, the list of another `Sequence` card and the column of the opened container all take it exactly like a toolbox item. A card the drag points at a place of is taken out of what drew it first (`Service.detachFromOwner`), a card that leaves the column is taken off the canvas (`adoptEmbedded` removes it from the diagram) and a card that enters it becomes a node of it again (`adoptSurface`), except into a target it carries itself, which would close a cycle. A region takes drops when the card is on a surface or drawn by an inline list (`ActivityRegion.acceptsDrop`), because a card drawn inside a branch is opened first. Its children have no ports or connections and keep no position of their own; a card drawn inside a card is an embedded node (`IsEmbedded`), exactly like a branch child. Ports are rendered only by the cards a graph container (`IGraphContainer`: `Flowchart`, `StateMachine`) lays out and marks through `DefaultNode.UseGraphPorts` (`DefaultNode.ShowsPorts`): the mode where the user connects elements to each other exists only there, while a card placed by any other container cannot start a link. Every edge carries the same point (`GraphPort`), which the base `PortModel` rules let join a link started at any point of another card, so the direction of a connection is the direction of the drag and not the edge; the right edge stays the anchor a link drawn from the model starts at (`DefaultNode.OutcomingPort`) and the left edge the one it ends at (`IncomingPort`), and `Service.LinkFromTo` takes the edge of a branch (`FlowchartNode.SourceEdge` — the bottom edge for the `False` branch of a decision and the default branch of a switch) unless the user drew the connection from another one (`Service.linkPorts`). A picked link offers its one command through `Service.LinkFromTo` (`Controls.AddFor` with `ControlsType.OnSelection`): `RemoveLinkControl` (its component is registered by the editor) deletes it, which `Links.Removed` translates into `TryDisconnect`, and the command is drawn on the route at the middle of it (`LinkCommandPositionProvider`) so the pointer that comes along the line finds the ends of the connection beside it. The connection itself is moved by taking one of its ends. `Service.pointerDown` takes the end of the route the press is nearest to (`Service.StartLinkEndDrag` with `Service.linkEndAt`, within `Service.LinkEndGrabRadius`), `Service.pointerMove` calls `Service.DragLinkEnd` once the pointer has moved past `Service.LinkEndDragThreshold` — so a press that does not move, or one on the middle of a long line, only picks the link — and that end follows the pointer on its own anchor (`Service.moveLinkEnd`), while `Service.pointerUp` calls `Service.DropLinkEnd`, which finds the connection point the pointer was released on (`Service.findPortNear`, within `Service.LinkEndSnapRadius`) and re-points the connection through `IGraphContainer.TryConnect`, keeping the branch the connection leaves (`FlowchartNode.SourceEdge`). A press on a connection point that a connection arrives at takes that connection instead: `Service.pointerDown` calls `Service.StartLinkEndDragFromPort` (`Service.incomingLinkOf` finds the link whose `Target` anchor is that point), which takes its target end and locks the point for the gesture (`Service.pressedPort`, released by `Service.DropLinkEnd`/`Service.CancelLinkEndDrag`), because the point is what the user grabs to move the connection away from the card. The library draws a new link on any press on a point, so it is registered again in the `Service` constructor — after the service subscribed — where it reads `PortModel.Locked` and leaves such a press alone; a press on a point no connection arrives at keeps drawing one. A drop away from every point, or on a point the container refuses, redraws the canvas from the model (`IGraphContainer.RebuildLinks`) and leaves the connection as it was: a connection is removed by its command. A release the canvas never sees — the pointer leaves it while an end is moving — is caught by `Service.pointerMove`, which puts the end back when the pointer moves with no button down (`Service.CancelLinkEndDrag`, also called by `Service.pointerDown` before a press takes an end), so a lost release cannot leave a line following the pointer. The name of a branch is drawn above the line (`LinkLabelModel.Offset`) because the command sits on it. A link the user draws is translated by the container that is open (`IGraphContainer.TryConnect`), which receives the edge it was drawn from: a card that keeps one outgoing branch (`FlowStep`, `State`) is re-pointed by the second connection, while a `FlowDecision` takes the right edge as its `True` branch and the bottom one as its `False` branch and a `FlowSwitch<T>` takes the right edge as a new case and the bottom one as its default branch, so a branch is moved by drawing it again instead of a further branch being added; the two edges state the branch they name, through `DefaultNode.PortCaption`, next to the port that carries them. A node that is deleted hands the connections that pointed at it to the one that ran after it (`FlowchartNode.redirect` over `Successors`), which keeps the start node of a `Flowchart` when the start node itself is removed. The `START` badge of the opened `Flowchart` is the handle of the choice the container keeps outside its canvas (`Service.BeginStartRebind`/`HoverStartTarget`/`RebindStart`, `FlowchartNode.SetStartElement`): the badge is dragged onto the card that should run first, which is outlined while the drag points at it. That choice is the card alone: `FlowchartControl` passes no `Preview` and no `Edit` to `ActivityControl` (the card carries its name and its `Open` action, like the card of a `Sequence`), which is why `FlowchartNode` no longer has `StartIndex`/`SetStart`. Neither `FlowchartNode.AddChild` (a dropped element becomes a `FlowNode` of the flowchart, with no `Next` set on any step and no start node chosen) nor `StateMachineNode.AddChild` (a dropped `State` is added to `States`, with `InitialState` left alone — it is chosen in the card of the machine through `FlowTargetSelect`) connects or starts anything. The card body shows one of two blocks: the compact fields a control passes as `Preview` while the card is closed, and the editor it passes as `Edit` while the card is open, where a container passes its child list as that editor. A card whose control passes no `Edit` has no chevron and no closed state. A card starts closed and the state is kept with the activity (`bwas:Designer.IsExpanded`), so it survives leaving the container and save/reopen. `Parallel` keeps a row of unordered branches with drops and deletes only.
- `Rethrow` and other unpaired loaded activities use the generic fallback: only the display name is editable. Do not describe them as having type-specific editors.
- Compared with the base Windows toolbox, remaining candidates are `ParallelForEach<T>`, `Pick`/`PickBranch`, and `Cast<T1,T2>`. `FinalState` needs XAML investigation before adding: Web already supports `State.IsFinal`.

## Adding or changing an Activity

1. Add the open generic Activity to the appropriate toolbox group in `WorkflowEditor.Web/Shared/MainLayout.razor`.
2. Implement a paired `DefaultNode` and Razor control using `[Pair(typeof(Activity), typeof(Control))]`. Keep workflow-model mutations in the node and UI in the control, and let a field the user clears take the expression of its argument away instead of leaving an empty one, which would not compile.
3. For containers, implement child loading, add, remove, and clear behavior. When the activity holds one Activity per branch, expose the branches as `IActivityHolder` slots (`DefaultNode.Slots`) instead of loading children, and render each one with `EmbeddedActivity`, so a drop fills the branch it landed on. A branch that hands the value on to its own activity is an `ActivityAction<T>` and the argument it reads it by has to be named differently from every argument of the activity that holds it: an expression compiler that ignores the case would read the two names as one, and the schema would fail to validate.
4. Add tests for editing, child management, invalid input, and XAML round-trip. Update the coverage list here when behavior changes.
5. Build and test the Web graph, then restart the local host before browser verification.
6. A designer that ships in a library of its own imports `Microsoft.AspNetCore.Components.Web` in its `_Imports.razor`. Without that import the Razor compiler leaves the `@bind-…` and `@on…` attributes of the card as markup: the build fails on a bound field, and the fields of a card stay inert without any error at all. `WorkflowEditor.TestActivities/_Imports.razor` carries the import for exactly that reason, and its tests cover the binding of a field.

Two limits of the runtime shape what a user activity can be:

- Several outputs of an activity are the branches of its card, not several connections of a graph node: `FlowNode`, `FlowStep`, `FlowDecision` and `FlowSwitch<T>` are sealed, so the graph only ever draws their own edges.
- An expression that reads a value a workflow passed in names a type of its own assembly, and the compiler of expressions has to be given that assembly and its namespace (`TextExpression.SetReferencesForImplementation` and `SetNamespacesForImplementation`) by whoever runs the schema.

## Verification

From the repository root:

```sh
dotnet test Blazor.WorkflowEditor.Tests/Blazor.WorkflowEditor.Tests.csproj -c Release
dotnet build web.slnf -c Release
```

`web.slnf` is the solution filter that holds the four Web projects (`Blazor.WorkflowEditor`, `WorkflowEditor.TestActivities`, `WorkflowEditor.Web` and the tests); `trunk.sln` also holds `WorkflowEditor.Win` and `glassPeople`, which target .NET Framework 4.7.2 and build on Windows only.

The style of the Web graph is checked as well:

```sh
dotnet format web.slnf --verify-no-changes --severity warn
```

`.editorconfig` asks for LF line endings and a UTF-8 byte-order mark on C# files, and `.gitattributes` keeps the line endings that way on every platform; the check covers the rest of the file — `using` order, blank lines, whitespace — and CI runs it before the tests.

The tests of `Blazor.WorkflowEditor.Tests` cover the workflow model and, through bUnit, the components: the toolbox panel (its groups, the search, the header that collapses it), the dialogs, and the editor component itself — what it draws for a workflow without a root activity, what it reports as unsaved, and what a validation run returns. The browser is faked there (loose JS interop plus the rectangle of the canvas), so a test covers what a component decides, while the diagram itself is still checked in the browser.

Run the host with:

```sh
dotnet run --project WorkflowEditor.Web/WorkflowEditor.Web.csproj --urls http://localhost:5199
```

After any rebuild, restart it and verify XAML open → edit → save → reopen in the browser.
